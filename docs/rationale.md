# Rationale moved out of source comments

Longer reasoning that used to sit above the code, kept here so the source stays short. One section per file.

## util/dot_pkce.gd

PKCE matters in a device flow because the device code travels to the backbone twice, at login start and on every poll. Without PKCE anything that observed the first exchange (a proxy, a log, a shared machine) could poll with the same device code and claim the token on approval; with it, redemption also needs the verifier, which never leaves the client. Only S256 is offered: `plain` makes the challenge the verifier, which protects nothing, and the backbone expects a 43-128 character challenge. The verifier is a secret with a ten-minute life, so it stays in memory; regenerating beats persisting. The challenge hashes the ASCII of the verifier string, not the bytes it decodes to; getting that wrong shows up only at redemption as a generic invalid-grant.

## util/dot_jwt.gd

A standard format rather than a bespoke one, because the properties that make it safe are the ones people get wrong when inventing: the signature covers the exact encoded header and payload, the algorithm is pinned by the verifier rather than read from the token, and expiry is checked against a bounded clock skew. RS256 and HS256 are what Godot's `Crypto` and `HMACContext` can do; there is no EdDSA. HS256 is symmetric, so whoever can verify can forge: fine when issuer and verifier are one process, disqualifying when hundreds of community servers verify a centrally issued ticket, since any one could mint tickets for any player. `DotAuthConfig` warns when HS256 crosses a trust boundary. The skew exists because a ticket refused for a server 20 seconds fast is a player who cannot connect for no visible reason. `verify` pins `expected_algorithm`: a verifier that dispatches on the token's own `alg` can be handed `{"alg":"none"}`, or an HS256 token signed with the RSA public key as the HMAC secret, which is public. Unverified claim reads are for logging and picking a `kid` only; an unverified token is a string an attacker wrote.

## server/dot_auth_ticket.gd

A player has an account on the backbone and a community-run server needs to know who they are. Sending the server the account token and letting it ask the backbone hands every operator a live credential for the whole site account, so the client instead asks a `DotAuthIssuer` the publisher runs (already trusted with the token) for a ticket naming one server, which the server verifies offline against the issuer's public key. Four properties, none droppable: audience-scoped (`aud` is the server id, so a malicious operator cannot replay captured tickets elsewhere), short-lived (minutes, only "asked for" to "connected"), single-use (`jti` remembered until expiry) and asymmetrically signed (with HS256 every verifying server could forge a ticket for any player). Passing `""` as the expected server id turns every ticket universal and is never correct in production. Reading the audience unverified is for routing in a multi-instance process only.

## server/dot_auth_provider.gd

The four built-in strategies cover the backbone, first-party introspection, local accounts and guests, not a console store, a chat service, a publisher's account service, a LAN token or a QA bypass; a game needing one should not fork dot-auth. Example:

```gdscript
class_name PlatformProvider extends DotAuthProvider

func _provider_name() -> String: return "platform"

func _handles(credential: Dictionary) -> bool:
    return credential.has("platform_ticket")

func _authenticate(credential: Dictionary) -> DotResult:
    var res := await _verify_ticket(credential["platform_ticket"])
    if not res.ok:
        return res
    var identity := DotAuthIdentity.new()
    identity.provider = "platform"
    identity.provider_id = res.value["account_id"]
    identity.uid = "platform:%s" % identity.provider_id
    identity.display_name = res.value["display_name"]
    return DotResult.success(identity)

# once, at startup
auth_server.add_provider(PlatformProvider.new())
```

Namespace uids: two platforms' account ids are both digits, and a ban on one would silently apply to whoever holds the other. `_handles` runs for every login attempt, including ones meant for another provider, so network work there is a cost on every login. A provider that claimed a credential and rejected it has made a decision, so the server does not fall through. `_validate` exists to fail at boot with a clear reason (missing API key, unreachable service) rather than on the first player's login.

## local/dot_local_profile_provider.gd

A `DotAuthProvider`, the existing extension point (its own docs name "a LAN token"), so a server offers local profiles and backbone tickets at once: the provider claims only credentials that name it. Folding the two credentials into "create it if the id is unknown" would turn every mistyped or expired credential into a new profile, so a player with a lost secret would become a stranger with their own name taken. The secret is emitted on `profile_created`, not put on the identity, because dot-server relays an identity to every player in the match; a secret there would be broadcast to the lobby. `is_guest` is false because the player holds a credential this server issued; it also governs mid-join renames (`DotAuthServer._apply_requested_name`), and a local profile's name lives in the store.

```gdscript
var local := DotLocalProfileProvider.new()
local.profiles = DotLocalProfiles.at("user://local_profiles.json")
local.profile_created.connect(_send_secret_to_that_client)
auth_server.add_provider(local)
# {"local_profile": {"id": "...", "secret": "..."}}   returning player
# {"local_profile_new": {"name": "Ashley"}}           first join
```

## local/dot_local_profile_client.gd

A local profile is a credential the server issued, so the client's whole job is to keep and present it. One file with one secret would present server A's credential to server B, fail, and silently mint a new profile on every server a player alternates between, losing the earlier secret; keying by server also means a server learns nothing about the player elsewhere. Encryption at rest is real protection against another user on desktop and mobile; on web the key is derived in the same origin as the ciphertext, so it is tamper-evidence and obfuscation there, about what a save file is worth. The passphrase is `OS.get_unique_id()` where available and a constant on web; it is deliberately not typed by the player (the threat is a curious sibling). An unreadable file (cleared browser origin, copied user directory, changed encryption setting) is treated as no file so the next join mints a new profile. An empty credential is the normal first state, not an error. `local_profile_client_path` was once never read, so every client used the default path whatever the config said.

```gdscript
var keeper := DotLocalProfileClient.at("user://local_profiles.dat")
keeper.open()
var credential := keeper.credential_for(server_id)
if credential.is_empty():
    credential = {"local_profile_new": {"name": chosen_name}}
keeper.remember(server_id, id, secret, name)  # the server answers a creation with the secret, once
```

## examples/issuer.gd

The publisher hosts the issuer; it alone holds the signing key or talks to the backbone with a player's token. Run it with `godot --headless --path . res://examples/issuer.tscn -- --auth-backbone-url https://moddingcommunity.com`, or add `--seconds 5` for a smoke test. It never exits on its own, so a blanket "run every example" sweep stalled on it once; `--seconds` bounds it because a headless Godot does not turn SIGTERM into a close request a Node can act on.

## bridge/dot_auth_admin_source.gd

Without the bridge every operator hand-edits a list of user ids; with it "everyone in the site group `moderators` can kick here" is one rule. It is duck-typed: dot-server looks for an object with `lookup` and calls it, so neither addon imports the other. `role_flags` is empty by default deliberately, because shipping a default would hand anyone with a site role control of every server; map roles only where operator and site are the same people. `group_flags` example: `{"moderators": ["kick", "mute", "chat"], "admins": ["kick", "ban", "changemap", "cvar"]}`. `authenticated_flags` suits servers where signed-in is itself a privilege (a reserved slot, chat). Per-user grants key on `uid`, never a display name. Immunity is the rule every admin system converges on: without it two admins kick each other in a loop with no winner. A failed lookup means this source has nothing to say, not an error.

## client/dot_auth_web_handoff.gd

A game embedded in a website meets a player already signed in there. The device flow is the wrong answer: reading a code off the canvas and typing it into the site they are on buys nothing, since the password is only ever typed on the website anyway. The site hands over a single-use code (valid about a minute, bound to one member and one game) exchanged for a credential pair scoped to the game, never a token, because the code travels through a document the site does not control; the worst a scraped code does is what that page was about to do anyway. The site's loader posts `{type: "tmc.auth", auth: {...}}` to the frame and the embedding page parks it on `window.__TMC_AUTH__`; never the query string, since a URL credential reaches history, referrers and frame-source logs. Nothing may use `DotWeb.eval`: the hosting page should send `script-src 'self' 'wasm-unsafe-eval'`, under which `JavaScriptBridge.eval` throws an `EvalError` the engine swallows, every read is null and nobody is signed in. The module reads the global as an object (`DotWeb.get_global`), which needs no CSP grant, which is also why the page publishes a `pending` marker rather than the game asking questions. Properties are read with `.name` because a JavaScriptObject forwards `.get("mode")` to a `get` method the page never defined. `pending` matters because a top-level tab that waited would spend that time on every launch outside the player. "Signed in" is distinct from "has a code": a member of a game that mints no identities arrives with no code, and a game unable to tell would prompt someone already signed in. `guests_allowed` is advisory; only the server can refuse a player.

## client/dot_auth_token_store.gd

The passphrase is a per-install random salt stored beside the ciphertext plus a device-stable string. That works against another user on the machine reading the file; against the owner or anything running as the same user it does not, the key is right there, and on web both halves share an origin. It still raises the cost of the common cases (synced backup, shared PC, stray file in a support bundle) and makes tampering detectable. The salt means two installs never share a key; the device string means a copied pair is unreadable elsewhere. The device string is deliberately coarse: an API that changes on OS update would lock players out on a routine upgrade, and being too stable only leaves the file readable by a machine that can already read the salt. A store that cannot be read is treated as no store because the usual cause is a device-identity change, not an attack. `is_access_valid` takes a margin because a token expiring in two seconds yields a request failing for a reason already ruled out. `clear` runs on sign-out and `token_reuse`, where keeping a dead token would only confuse the next launch.

## dot_auth_identity.gd

`uid` is what bans and admin entries key on, so it is never reassigned and never player-changeable; namespacing by provider (`backbone:clx8f...`, `local:admin`, `guest:a3f9...`) stops two backends colliding and keeps a ban list meaningful when a server switches backends. `role` is advisory because treating site staff as server admins would let anyone with a site role walk into every server running this addon. Guests get a stable per-device id so they can be muted or kicked within a session, nothing that survives a reinstall. `from_backbone_user` mirrors the contract file exactly; a drift shows as an empty display name rather than a crash, which is why only `uid` is validated. The introspection identity carries no account id: two operators comparing logs learn nothing, and bans hold per server. `has_claim` normalises because claims arrive as JSON. `describe` includes the uid because moderation notes that record only a name are useless once the name changes.

## backbone/dot_backbone_client.gd

A server reporting its own player count, map and roster is better data than a scraped listing: no packet loss, no rate-limited A2S, no list truncated at 255. Every request carries `ts` and `nonce`; the backbone refuses anything outside its skew window and remembers nonces inside it, so a reporter omitting them still gets the window but sending both closes the gap. The registry name exists because `DotCloudClient` went unregistered the same way and four call sites found null without erroring, since "no cloud client" is a legitimate configuration. The client is built by whatever owns the server credential and consumed by things that cannot reach it; handing it over through the registry avoids per-consumer plumbing and ordering bugs (a consumer built during module load precedes any host assignment). The state callable is sampled at send time. `report_users` is absolute because incremental needs guaranteed delivery of every join and leave; `SERVER_USERS` is separate from `SERVER_STATS` since a player list is personal data about third parties. Name resolution is narrow on the backbone side (within an entitled party, members who joined themselves) and must not be used as a general lookup. Milliseconds in `ts` are refused loudly, so the stamping is made impossible to get wrong here instead of at four call sites.

## local/dot_local_profiles.gd

For a deployment with no cloud that wants accounts anyway (a LAN server, a friends' server, a game shipped without accounts). The identity is a credential this server issues, because every alternative is worse. A name is what an offline mode does, and anyone who types your name is you: fine among six friends, indefensible on a public server. A machine id (`device_hint`) is deliberately not the identity: `OS.get_unique_id()` returns nothing on web and iOS, it is just a string the client sends so it is as forgeable as a name while looking authoritative, and it is stable across accounts so two people on one machine would be one player. A password puts a login form in front of someone who wanted to play and lands a password store on a game server (`DotAuthServer.hash_password` says why that is nothing to be proud of). So the server mints an id and a 32-byte secret on first join, stores only a salted hash, and gives the secret to the client once; the client keeps it per server and presents it next time, a session cookie for the same reasons. The secret is scoped to one server so a leak is that server's problem, the same property the platform rests on. The id is 22 base64url characters, the shape `DotUserScope` derives and `DotAvatarKey.is_usable` accepts, so profile and avatar stores work unchanged and nothing downstream branches on account kind.

```gdscript
var profiles := DotLocalProfiles.at("user://local_profiles.json")
profiles.open()
var made := profiles.create("Ashley")           # first join: {"id": ..., "secret": ...}, send the secret to that client
var who := profiles.verify(id, secret)          # every join after
```

The hash rounds are not protecting a guessable password: an offline attack on a 256-bit secret does not terminate. They exist so a leaked file is not a list of usable credentials, and to close the case of an operator letting someone choose their own secret. `max_profiles` is a backstop: a server letting an unauthenticated visitor write a row has handed the disk to the internet, and the connection rate limit is the first line. Duplicate names are refused because two "Ashley"s reintroduces impersonation at the layer people look at. `device_hint` is stored on creation and compared on verify only to log that a profile moved machine, useful for an operator and terrible to enforce, since people replace computers and browsers clear storage. The secret is unrecoverable: a caller that drops it has locked that profile out, the right trade against a server holding usable credentials for everyone. `verify` is constant-time because otherwise it leaks how many leading characters were right. `remove` does not require the secret because the console needs it for abusive players. `save` goes through `DotPaths.write_json` (temp file and rename) so an interrupted write loses a change, not every account. Ids are restated, not imported, from `DotAvatarKey.is_usable` because dot-auth does not depend on dot-user-avatar.

## server/dot_auth_session_reporter.gd

The issuer learns a player is going somewhere when it mints their ticket; it learns they arrived, and later left, from this. A server without one still works with the rule on, but players are held for the lease after their ticket, so it cannot free a player the moment they leave nor hold one for a whole match. Reports are the whole roster, as `DotBackboneClient` reports to the site, so the host supplies a callable and a lost report costs one interval, not a stuck record. A host rarely builds one: `DotAuthServer` creates it as a child when `session_report_url` is set and points it at the registry's `dot_server` with `follow_server`. By hand:

```gdscript
var reporter := DotAuthSessionReporter.new()
reporter.config = auth_config           # session_report_url, _key, server_id
reporter.roster_provider = func() -> Array:
    return my_players.map(func(p): return p.uid)
add_child(reporter)
reporter.report_offline_now()           # before the process stops
```

Which shutdowns say goodbye: the empty roster goes out, blocking for at most `offline_timeout_sec`, when a followed server enters SHUTTING_DOWN and when this node leaves the tree, which `SceneTree.quit()` (console `quit`, a scheduled restart) does to every node. It blocks because both happen with the process about to end and an asynchronous request is freed with the tree before it is answered. SIGINT and SIGTERM do not reach here (headless Godot runs no notification for them), so Ctrl+C, `kill`, a container stop or a crash leaves players to the lease. The key is the per-server bearer token the publisher issues, sent over the reverse proxy's TLS like a player's access token to `/ticket`. Past the issuer's request cap a report can no longer say "absent means gone" for everybody; truncating with a warning is the honest failure, since staying silent would hold everyone for the lease. `report_offline` goes through `DotHttp`, an `HTTPRequest` the tree polls, which is freed before the issuer answers when the tree is torn down; `report_offline_now` drives an `HTTPClient` in a loop on the calling thread, not on web where `fetch()` cannot be waited for (a tab is never a server anyway). Following a server: duck-typed so dot-auth names nothing of dot-server's; the roster is every signed-on session, because a player loading a map or reloading through a game change is still on the server, and omitting them would end a confirmed session and let them take a ticket for another server mid-load. The reference is weak: a server that went away leaves the provider answering null, and an unknown roster is not sent because an empty one would free everybody still playing. Guests are dropped since they never held a ticket and would only fill the issuer's table with per-device ids.

## dot_auth_config.gd

`backbone_url` was once `https://themodcommunity.com`, which is not TMC's domain and was unregistered when found. Every deployment that did not override it pointed its device-code grant at a name any stranger could buy; it failed loudly only because the name did not resolve, and the day someone registered it it would have failed quietly, which is worse. The wrong name travelled from here into three READMEs. Override per deployment: `DOT_AUTH_BACKBONE_URL`, `--auth-backbone-url` and a JSON file, in that layering; a browser build has no environment or argv, so it reads the JSON its build ships (dot-server-deploy's `client/auth.json`). It is never read from the page's query string, because it decides where a single-use sign-in code is redeemed. `first_party_audiences` entries are `server:<id>` or `app:<id>`; the client mints a join token via `POST /api/app/v1/play/join-token` for exactly that audience and sends that, never its access token; a server claiming another's audience gains nothing; empty means a ticket (when an issuer is configured) or a refusal. The backbone refuses a device access token on INTROSPECT, so an older client is told to update rather than leaking a credential. `join_audience` empty is read from `GET /api/integration/v1/me`; a wrong value is not a hole, only a broken join. The device approval label is untrusted by the backbone but is what the player reads. Poll interval: polling faster than told is how a client gets its grant burned; going past the 10 minute grant TTL only yields `expired_token`. On web the token encryption is obfuscation because the key lives in the ciphertext's origin. `server_id` is the ticket audience: a ticket for `eu-west-1` must not be accepted by `us-east-2`. The ticket TTL is minutes because it only spans "asked for" to "connected"; replay memory must exceed it or a ticket can be replayed in the gap. `allow_guests` is for casual servers; a guest can come back as a different guest, so turn it off where bans matter. `session_report_url` makes `single_session` mean anything because a ticket is only an intention to connect; the reporting turns "asked for a ticket" into "on this server now" and releases players when they leave. `session_report_key` is per server, issued by the publisher; without it anyone could report any player onto any server and lock them out everywhere else for the lease on the strength of a POST. `session_report_sec` must leave room to lose a report or two (half the lease at most; defaults 60 against 300) or players drop out of the issuer's records between reports. `local_profiles` is independent of `strategy` since it is a provider, so a player with no site account is not turned away from a game whose others have one; `Strategy.LOCAL` is an operator-maintained file for a known cast, while this is self-service. `local_profile_client_path` is on the shared config because a client storing it in the wrong place silently loses every local profile. `single_session` lives on the issuer, the only participant that sees every server: servers comparing notes would mean operators trusting each other, which tickets exist to avoid. A player on `eu-west-1` asking for `us-east-2` is told where they are and refused until they leave, the server reports them gone, or the lease runs out; a ticket for the server they are already on is always granted so a crashed client can reconnect. The lease is the clock between reports and the hold time of a non-reporting server: too short and a lost report frees everybody, too long and a dead server locks players out; it must be at least the ticket TTL, or a player could hold a live ticket for one server after the issuer has forgotten it and get a second. The integration token is scoped to one server by the backbone; the roster needs `SERVER_USERS`, kept separate from `SERVER_STATS` as personal data about third parties. The per-minute request ceiling keeps a retry loop from getting the integration credential rate-limited or revoked.

## client/dot_auth_client.gd

A game asking for account credentials trains players to type them into game clients, which every phishing attempt relies on. The device flow keeps the password on the website, and it is the only flow that works unchanged on a console, a TV and a browser build that cannot open a popup.

```gdscript
var auth := DotAuthClient.new()
add_child(auth)
auth.config = my_config
auth.device_code_ready.connect(func(user_code, url, _expires):
    code_label.text = user_code
    OS.shell_open(url))
var res := await auth.sign_in()
if res.ok:
    print("hello ", (res.value as DotAuthIdentity).display_name)
```

Handoff acceptance is on by default because a game inside the TMC player that ignored it would ask a signed-in member to sign in again; turn it off for a build distributed to sites you do not control, where "who is playing" should come from your own backend. The page's handoff comes before stored credentials as a correctness order, not an optimisation: a browser build's store is per origin, so two members on one computer, or one who signed out of the site and in as someone else, would be seated as whoever the storage last held; a stored session is the right fallback and the wrong first answer. The handing page's origin replaces the configured backbone URL: the redeem URL is absolute and redeems fine on a staging or self-hosted site, but every later call would otherwise go to the compiled-in site with a token it does not recognise. The launcher variant sends the code to the configured backbone only: a native process has no page that is the backbone, and a redeem URL from argv would let whoever wrote a shortcut aim a member's code at a host of their choosing. The page block usually arrives while the WASM downloads; the wait is for a loader that posts on frame load racing a cached export that boots at once, which would otherwise seat a signed-in member as a guest. An empty read is final because the page publishes `pending` while waiting, and waiting anyway would cost every launch outside a player the full timeout. A `token_reuse` response means a retired refresh token came back, a race or theft; the backbone has signed out every device, so the store is cleared and the player told. A local-only sign-out exists because a sign-out that fails offline would be one that does not happen. Ticket requests go by the address this client dialled, never an announced id, because a hostile server naming another's id would get a ticket valid there; the nonce binds the ticket to the connection. The join token is spent once within sixty seconds by the audience's credential only, refused by every app API route, and refuses audiences outside `first_party_audiences`. `release_session` is the polite half of `single_session`: the server's own report may be a minute away, and a player who quit one server to join another should not be told they are still on the first. The issuer's refusal text is written for the player ("You are already connected to eu-west-1" beats "Not allowed.").

## server/dot_auth_issuer.gd

The issuer is the missing piece between "the backbone knows who you are" and "a community server can find out without holding your account token": a client sends its backbone access token (first-party trust) and gets a ticket scoped to one server, valid for minutes and verifiable offline with the public key. Run it headless next to the publisher's other services (`examples/issuer.tscn` with `--auth-issuer-private-key-file keys/issuer.key --auth-server-port 8787`); it is the only component needing the private key and outbound backbone access.

The built-in listener is `TCPServer`-based and speaks enough HTTP/1.1 for one JSON POST: no TLS, keep-alive or chunked encoding. TLS, real request limits and access logs belong in a reverse proxy; at port 0 call `issue_for_token` to embed the issuer elsewhere. Because every ticket passes through the issuer it alone can know a player is already on some server, and with `single_session` it refuses a second: a ticket opens a session, the server confirms and later closes it by reporting its roster to `POST /session` with its key, a player closes their own with `POST /session/release`, and a lease closes whatever nobody reported on.

The key file is preferred over `issuer_private_key` because a config can be dumped into a log. An open allow-list mints a ticket naming any string, and an allow-list also stops a typo'd id from yielding tickets that never verify. Server keys live in a file, not an inspector field, because a scene is no place for secrets; one per server so a leak is rotated for one operator and a report speaks only for its own server. A ticket request is a few dozen bytes and a full roster about 20 KB, which sets the body limit. The request deadline bounds the whole request because a byte-a-second sender never looks idle and would hold a slot while staying under every per-read limit. Connections are capped with 503 because every held connection is polled each frame, so an unbounded list turns idle sockets into the issuer's frame budget.

A session begins unconfirmed when a ticket is minted (the player said where they are going) and is confirmed when that server reports them. A report is the whole roster. An unconfirmed session omitted from it is left alone, because the report is truthful (they have not arrived) and acting on it would let a player fetch tickets for two servers between the first mint and the first roster naming them; it lapses on its own. A listed player recorded on another server is moved: the report is the truth, and refusing it would hold them on a server they left. Releasing is the common case of a player leaving and need not wait for a report. A reconnecting confirmed player keeps a confirmed session, or a roster briefly omitting them could not end it. The public identity-based mint skips a backbone round trip and lets the session rules be tested without a backbone.

Token lookups are rate-limited per hashed token so one compromised account cannot exhaust everyone's budget and the token is not kept in a dictionary. Key comparison is constant-time and identical for unknown server and wrong key. Requests are not delivered one per read: parsing what one poll saw treats a segment boundary as the request's end, hence accumulation against Content-Length; the header end is searched over bytes because a body split mid-UTF-8 decodes to a replacement character and shifts every offset. `POST /session` is rate-limited under the server's name so a stuck reporter cannot crowd out tickets, and refuses a wrong key before reading the roster. Release resolves through the backbone like a ticket request, so a token can only end its own account's session.

## server/dot_auth_server.gd

The same server binary is a public ticket-verifying server, a first-party introspecting one, a LAN server with a local account file or an open anonymous one, depending on `DotAuthConfig.strategy`. It registers as `dot_auth_server` in the registry so dot-server finds it with no hard dependency either way.

```gdscript
var res := await auth.authenticate({"ticket": ticket_from_client, "name": requested_name, "device_id": client_device_id})
if not res.ok:
    session.reject(res.error.message)
    return
session.identity = res.value
```

Why the auth server builds the session reporter: the reporter's lifetime is the server process's and its config is this node's (issuer key, URL, server id are `DotAuthConfig` fields the host already hands here). dot-game's `DotGameModule` is per game, so a game change would unload it with every player still connected (it could neither say goodbye nor stay silent honestly), and several games are not on it; games never own authentication, and the host's `dot_auth_server` is the same for every game it runs. dot-server never names dot-auth. So it lives beside the config it reads and reaches dot-server by duck type through the registry. With `backbone` set, INTROSPECT calls `POST integration/v1/player/introspect` as this server and gets the player's key in this server's scope: the only identifier the backbone's avatar, profile and stats routes resolve here, and one other operators cannot correlate. Unset, it reads `/api/app/v1/me`, which answers with the account id, is for first-party servers only, and fails for a current client whose join token `/me` refuses. A host that hands the client over after boot (the listener opens before the integration credential loads) would let a player in through `/me` keyed by account id, a different identity from the one they get a minute later, splitting profile, avatar and bans; hence the refusal option. Refusal-run escalation: a single refused ticket (expired, from the wrong server) is the player's problem; ten in a row with nobody getting in is almost always this server's (a `ticket_public_key` from another deployment, a mismatched `server_id`, a drifted clock), and nothing else in the process can tell them apart, while every one reads to the player as "the server will not let me in". The local provider is held so `describe` can report it and an operator's "remove that player's profile" command can reach it without searching providers by name. Custom providers are validated at registration so a missing API key fails at boot. Rate limiting runs before providers so a custom provider that calls an external service cannot be used to make this server hammer it. A provider that claims a credential owns the outcome; one that recognised a platform ticket and rejected it has decided, and falling through would let a refused login in by another door. The shared finish step gives provider and built-in paths the same guest fallback, counters and signals. Log levels follow the family rule by who must act: a refused credential is INFO (admins keep failed sign-ins since they are what a guessing attack looks like), rate limiting is the limiter doing its job at DEBUG, an unreachable verifier is WARN once per outage in `_finish` with each refusal it causes at DEBUG, and the server's own faults (unknown strategy, a failed provider, an unreadable file) are ERROR. Never log the credential: no password, token or ticket. The username is logged since guessing is aimed at it and an operator needs it to see one. Scoped identities carry no account id: the uid is `tmc:<key>` and the key is the `scoped_key` claim dot-user files the profile under. Replay memory must exceed the ticket TTL (validated) or a ticket could outlive the record of having been spent. A join token (or a legacy web build's game token) through `player/introspect` yields a scoped key and leaves the operator nothing to replay.

## examples/auth_demo.gd and examples/session_reporter_selftest.gd

The demo covers what can be tested without a backbone: ticket minting and offline verification, audience scoping (a ticket for server A refused by B), replay refusal, connection binding (a copied ticket refused on another connection), issuer key rotation overlap and revocation, expiry and clock-skew leeway, payload tamper detection, algorithm confusion (an HS256 token where RS256 is expected), PKCE derivation, local accounts with a wrong password and an unknown user, the admin-source mapping, a token-store round trip through encryption, and one seat per account including every way a session ends over a real socket. The roster path runs over the issuer's own listener because the endpoint is the one part a unit call cannot reach, and the family's record is that the bug is always in the part nothing ran. The registry check exists because `DotCloudClient` went unregistered and four call sites found null without erroring. The flat-refusal check exists because the client once read only a nested `error` object the site never sends, so every refusal through `post_app`/`get_app` came back as fallback text with the site's code lost. The server once counted a refusal, emitted a signal and said nothing, so "why can I not get in" had no answer in its own log; each refusal is now logged at the level of whoever must act.

The reporter selftest uses real `DotServer`s with a `DotAuthServer` child as dot-server-deploy's host places it. The issuer's socket is a fake on a thread: the goodbye a stopping server sends is synchronous (the tree is being torn down), and the real listener is polled from `_process` on the main thread that is blocked waiting for the answer. The thread accepts the request, answers 200 and records it, and the main thread hands each recorded roster to the issuer's public `authorize_server` and `report_sessions`, which is what its `/session` route does. Armed by `create_session_reporter` defaulting to false, or `_exit_tree` / `follow_server` removed: the "freed" checks fail; the last section is that control, kept in the suite.
